01 SDK architecture

One governing rule shapes every decision below: the SDK must never be able to slow down, block, or crash the host application — not on a slow network, not when the platform is down, not under load. Everything else is in service of that.

Four layers, each independently testable:

  • Public API — IrpClient, the only thing application code touches. Every method returns immediately.
  • Event model — plain immutable records that mirror the Phase 1 ingestion DTOs, so the mapping to HTTP payloads is mechanical, not creative.
  • Async dispatch — a bounded in-memory queue plus one background worker thread that batches events and sends them off the caller's thread entirely.
  • HTTP transport + retry — a small wrapper over java.net.http.HttpClient (no extra HTTP library dependency to drag into every consumer's classpath) with backoff on transient failures.

Two Maven modules, not one, because not every consumer is Spring: irp-client-core has zero Spring dependencies and works in any Java 21 app; irp-spring-boot-starter depends on core and adds the Spring-specific glue (auto-configuration, the latency filter, the exception resolver).

02 Spring Boot starter design

The starter's whole job is to turn "add one dependency" into a fully working, auto-wired IrpClient plus two automatic capture mechanisms, with every piece overridable and disableable. It follows the same shape as any real observability starter (Sentry, Datadog): one @AutoConfiguration class, one @ConfigurationProperties record, and small focused beans behind @ConditionalOnProperty/@ConditionalOnMissingBean guards.

IrpClient bean

Always registered if irp.api-key is set. Consumers can define their own bean of the same type to fully override it.

Latency capture filter

Only registered in a servlet web application, and only if irp.latency-capture.enabled (default true).

Exception capture resolver

Only registered in a servlet web app, only if irp.error-capture.enabled (default true). Never swallows the exception.

Health reporter

Optional scheduled heartbeat calling sendHealthStatus(), off by default — irp.health.auto-report.enabled.

03 Auto-configuration approach

Spring Boot 3 dropped the old spring.factories mechanism in favor of an explicit imports file — using it (not the deprecated path) is itself a small signal of currency worth having in a portfolio project.

com.irp.sdk.spring.autoconfigure.IrpAutoConfiguration
IrpAutoConfiguration.java 
// Core config: registers the client itself. Works in ANY app, web or not.
@AutoConfiguration
@EnableConfigurationProperties(IrpProperties.class)
@ConditionalOnProperty(prefix = "irp", name = "enabled", havingValue = "true", matchIfMissing = true)
@ConditionalOnProperty(prefix = "irp", name = "api-key")
public class IrpAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public IrpClient irpClient(IrpProperties properties) {
        return new DefaultIrpClient(properties);
    }

    // Nested so it only activates inside a servlet web app - a batch job
    // or CLI tool that pulls in the starter should NOT get a Filter registered.
    @Configuration
    @ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
    static class WebConfiguration {

        @Bean
        @ConditionalOnProperty(prefix = "irp.latency-capture", name = "enabled", havingValue = "true", matchIfMissing = true)
        public FilterRegistrationBean<IrpLatencyCaptureFilter> irpLatencyFilter(IrpClient client, IrpProperties props) {
            var registration = new FilterRegistrationBean<>(new IrpLatencyCaptureFilter(client, props));
            registration.setOrder(Ordered.HIGHEST_PRECEDENCE + 10);
            return registration;
        }

        @Bean
        @ConditionalOnProperty(prefix = "irp.error-capture", name = "enabled", havingValue = "true", matchIfMissing = true)
        public IrpExceptionCaptureResolver irpExceptionCaptureResolver(IrpClient client) {
            return new IrpExceptionCaptureResolver(client);
        }
    }

    @Bean
    @ConditionalOnProperty(prefix = "irp.health.auto-report", name = "enabled", havingValue = "true")
    public IrpHealthReporter irpHealthReporter(IrpClient client, IrpProperties props) {
        return new IrpHealthReporter(client, props);
    }
}
Design decision: the exception resolver implements HandlerExceptionResolver and always returns null after capturing — that tells Spring "I didn't handle this, keep looking." It reports every exception to the platform without ever interfering with the host app's own @ExceptionHandlers or error pages. An SDK that changes the host app's error responses is an SDK nobody will actually install.

05 Main client class

IrpClient.java (public interface — the only thing consumers depend on) 
public interface IrpClient {
    void captureException(Throwable throwable);
    void captureException(Throwable throwable, Map<String, Object> metadata);
    void trackEvent(String name, Map<String, Object> metadata);
    void markDeployment(String version, String commitHash);
    void sendHealthStatus();

    /** Flushes any buffered events, waiting up to the given timeout. Call on graceful shutdown. */
    void flush(Duration timeout);
}
DefaultIrpClient.java 
public class DefaultIrpClient implements IrpClient, SmartLifecycle {

    private final IrpProperties properties;
    private final EventDispatcher dispatcher;

    public DefaultIrpClient(IrpProperties properties) {
        this.properties = properties;
        this.dispatcher = new EventDispatcher(properties, new HttpTransport(properties));
    }

    @Override
    public void captureException(Throwable throwable) {
        captureException(throwable, Map.of());
    }

    @Override
    public void captureException(Throwable throwable, Map<String, Object> metadata) {
        dispatcher.enqueue(ErrorEvent.from(throwable, properties.serviceName(), metadata));
    }

    @Override
    public void trackEvent(String name, Map<String, Object> metadata) {
        // Phase 1's backend has no generic "custom event" endpoint yet - see §6 for
        // why this is mapped onto the existing log-ingestion path instead of blocking
        // SDK delivery on a backend change.
        dispatcher.enqueue(LogEvent.trackEvent(name, properties.serviceName(), metadata));
    }

    @Override
    public void markDeployment(String version, String commitHash) {
        dispatcher.enqueue(DeploymentEvent.of(version, commitHash, properties.serviceName()));
    }

    @Override
    public void sendHealthStatus() {
        dispatcher.enqueue(LogEvent.health(properties.serviceName()));
    }

    @Override
    public void flush(Duration timeout) {
        dispatcher.flush(timeout);
    }

    // SmartLifecycle: start the worker thread when the app context is ready,
    // and flush + stop it cleanly on shutdown instead of dropping in-flight events.
    @Override public void start() { dispatcher.start(); }
    @Override public void stop() { dispatcher.stop(properties.readTimeout().multipliedBy(2)); }
    @Override public boolean isRunning() { return dispatcher.isRunning(); }
}

Notice every public method does exactly one thing: build an immutable event object and hand it to the dispatcher. There is no I/O, no blocking call, and no exception that can propagate back to the caller from any of these methods — enqueue() is designed to never throw (see §7).

06 Event model

The SDK's event types don't map one-to-one onto the four public methods — they map onto what Phase 1's backend can actually ingest today: /api/v1/ingest/logs, /errors, and /deployments. That gap is deliberate and isolated to one place.

Design decision: trackEvent() and sendHealthStatus() currently serialize as LogEvents (level INFO, with a reserved metadata.__irp_type__ marker of TRACK or HEALTH). This means zero backend changes are needed to ship this SDK today. When a later phase adds dedicated /ingest/events and /ingest/health endpoints, only HttpTransport's routing changes — the public IrpClient API and every line of a consumer's code stays identical. That's the entire reason the event model is a separate layer from the transport layer instead of one class.

    }

07 Async sending design

The caller's thread only ever does one cheap, non-blocking thing: queue.offer(event). Everything expensive happens on a single dedicated background thread.

transport/EventDispatcher.java 
public class EventDispatcher {

    private final BlockingQueue<IrpEvent> queue;
    private final HttpTransport transport;
    private final IrpProperties.Queue config;
    private final ExecutorService worker;
    private final AtomicLong dropped = new AtomicLong();
    private volatile boolean running;

    public EventDispatcher(IrpProperties properties, HttpTransport transport) {
        this.config = properties.queue();
        this.queue = new ArrayBlockingQueue<>(config.capacity());
        this.transport = transport;
        // Daemon thread: never blocks JVM shutdown on its own.
        this.worker = Executors.newSingleThreadExecutor(r -> {
            Thread t = new Thread(r, "irp-sdk-dispatcher");
            t.setDaemon(true);
            return t;
        });
    }

    /** Never blocks, never throws. Called directly from application/request threads. */
    public void enqueue(IrpEvent event) {
        if (!queue.offer(event)) {
            long total = dropped.incrementAndGet();
            if (total == 1 || total % 500 == 0) {
                log.warn("IRP SDK: event queue full ({} capacity) - dropped {} events so far. " +
                        "The platform may be unreachable or too slow.", config.capacity(), total);
            }
        }
    }

    public void start() {
        running = true;
        worker.submit(this::runLoop);
    }

    private void runLoop() {
        List<IrpEvent> batch = new ArrayList<>(config.batchSize());
        while (running || !queue.isEmpty()) {
            batch.clear();
            IrpEvent first = poll(config.flushInterval());
            if (first == null) continue;
            batch.add(first);
            queue.drainTo(batch, config.batchSize() - 1);
            transport.sendWithRetry(batch);
        }
    }

    public void flush(Duration timeout) { /* drains queue synchronously, bounded by timeout */ }
    public void stop(Duration timeout) { running = false; flush(timeout); worker.shutdown(); }
    public boolean isRunning() { return running; }
}

Why a bounded queue and drop-on-full, not an unbounded one

An unbounded queue turns "the platform is briefly slow" into "this app runs out of memory." A bounded queue with drop-and-log is the same trade-off every serious telemetry SDK makes: observability data is allowed to be lossy under extreme conditions; the host application's stability is not allowed to be.

08 Retry design

transport/HttpTransport.java (retry logic) 
void sendWithRetry(List<IrpEvent> batch) {
    Map<EventType, List<IrpEvent>> byType = batch.stream().collect(groupingBy(IrpEvent::type));

    for (var entry : byType.entrySet()) {
        String path = endpointFor(entry.getKey());   // logs / errors / deployments
        int attempt = 0;
        Duration backoff = retry.initialBackoff();

        while (true) {
            try {
                HttpResponse<Void> response = send(path, entry.getValue());
                if (response.statusCode() < 300) return;

                if (response.statusCode() == 401) {
                    log.error("IRP SDK: API key rejected (401) - check irp.api-key. Not retrying.");
                    return; // will never succeed - don't waste retries
                }
                if (response.statusCode() < 500) {
                    log.warn("IRP SDK: batch rejected ({}), dropping. Not retrying a client error.", response.statusCode());
                    return;
                }
                // 5xx - transient, worth retrying
            } catch (IOException | HttpTimeoutException e) {
                // network failure - transient, worth retrying
            }

            attempt++;
            if (attempt >= retry.maxAttempts()) {
                log.warn("IRP SDK: giving up on a batch of {} events after {} attempts.", entry.getValue().size(), attempt);
                return;
            }
            sleep(backoff);
            backoff = min(backoff.multipliedBy(2), retry.maxBackoff())
                    .plus(Duration.ofMillis(ThreadLocalRandom.current().nextInt(100)));  // jitter
        }
    }
}
FailureRetried?Reasoning
Network error / timeoutYes, up to max-attemptsTransient — the platform or network may recover
5xx responseYes, up to max-attemptsServer-side issue, likely transient
401 UnauthorizedNoA bad API key will never start working mid-retry-loop
4xx (other)NoA malformed request will fail identically every retry

Backoff is exponential with jitter (initialBackoff × 2^attempt, capped at maxBackoff, plus a small random offset) — the jitter matters once more than one instance of the same service is retrying at once, so they don't all hammer the platform back in perfect unison.

@RestController
@RequiredArgsConstructor
public class CheckoutController {

    private final IrpClient irp;
    private final CheckoutService checkoutService;

    @PostMapping("/checkout")
    public CheckoutResponse checkout(@RequestBody CheckoutRequest request) {
        irp.trackEvent("checkout.started", Map.of("cartSize", request.items().size()));

        try {
            return checkoutService.process(request);
        } catch (PaymentDeclinedException e) {
            // The starter's exception resolver already reports UNCAUGHT exceptions
            // automatically. This manual call is only useful because it attaches
            // extra business context the automatic capture can't know about.
            irp.captureException(e, Map.of("orderId", request.orderId(), "amount", request.amount()));
            throw e;
        }
    }
}

Same split as the core platform's own Phase 1 shape: a plain-Java module that could theoretically be reused outside Spring one day, and a thin Spring-specific shell around it. The starter module has exactly one job — wire beans — and contains no business logic of its own.

11 Implementation steps

1
Scaffold both modules

Parent POM, two child modules, dependency direction locked (starter → core, never the reverse).

2
Event model

IrpEvent sealed hierarchy + the three record types, with unit tests for the trackEvent/health → LogEvent mapping decision.

3
HTTP transport

HttpTransport using java.net.http.HttpClient, mapping each EventType to its ingestion path, with a mock server (e.g. WireMock) in tests.

4
Async queue + worker

EventDispatcher: bounded queue, batching, drop-on-full with the rate-limited warning log.

5
Retry policy

Exponential backoff with jitter; unit test the 401-never-retries and 5xx-does-retry branches explicitly.

6
IrpClient facade

Wire dispatcher + transport behind the four public methods plus flush(); implement SmartLifecycle for clean startup/shutdown.

7
Starter: properties + auto-configuration

IrpProperties record, IrpAutoConfiguration, the AutoConfiguration.imports file.

8
Latency capture filter

IrpLatencyCaptureFilter as a OncePerRequestFilter; respect slow-threshold.

9
Exception capture resolver

IrpExceptionCaptureResolver; verify it never changes the host app's actual error response in a test app with its own @ExceptionHandler.

10
Sample app + manual verification

A throwaway Spring Boot app depending on the starter via mvn install to the local repo — this is also the demo app for Phase 1's original demo script.

11
Graceful shutdown test

Confirm events queued right before shutdown are actually flushed, not silently dropped, within the bounded timeout.
