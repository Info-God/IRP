1Project Overview

What this project is, in plain language, and why it was built this way.

The Agentic AI Incident Response Platform (IRP) is a system that helps engineering teams find out why something broke in production — faster, and with an AI assistant doing the first pass of investigation instead of a human staring at logs at 3 AM.

It is built as four separate, independently-runnable pieces that talk to each other over HTTP, mirroring how real incident-response products (PagerDuty, Datadog, Sentry) are actually structured:

Phase 1 — project/ Complete

A Java Spring Boot backend: the system of record. Stores organizations, projects, incidents, logs, errors, deployments, API keys, and an audit trail.

Phase 2 — incident-sdk/ Complete

A Java library that any other Spring Boot application can add as a dependency to automatically report errors, slow requests, deployments, and custom events to Phase 1.

Phase 3 — irp-ai-service/ Partial

A Python FastAPI service that uses an LLM (Groq/Llama 3.3) to investigate an incident — reading logs/errors/deployments and proposing a root cause for a human to approve.

Phase 4 — dashboard/ Partial

A React + TypeScript dashboard where a human reviews incidents and the AI's suggestions, and approves or rejects them. Runs on realistic mock data by default.

The project was built in this order — backend first, then the SDK that feeds it, then the AI layer that reads from it, then the dashboard that visualizes it — because each phase depends on the one before it actually existing and having a stable API.

2Problem We Are Solving

The real-world incident response problem in cloud/backend systems.

Modern backend systems (checkout services, payment gateways, notification workers, etc.) run as many small services talking to each other over a network. When something goes wrong — a null pointer exception, a timeout, a bad deployment — the failure usually shows up as a flood of log lines and error events scattered across several services, not one clear message saying "here's the bug."

What actually happens today in most teams

  • Alert fatigue — engineers get paged for everything, so real incidents get lost in noise.
  • Manual root-cause digging — someone has to open five dashboards, correlate timestamps, and guess what changed (a deploy? a config change? a dependency going down?).
  • Slow MTTR (Mean Time To Resolution) — the time between "something broke" and "we know why and fixed it" directly costs money and trust.
  • No audit trail — when something is fixed under pressure, teams often forget to record what happened or why, which hurts post-mortems and compliance.
  • Fear of AI automation — teams want AI to help investigate, but do not want an AI executing changes (rollbacks, restarts) without a human checking its reasoning first.

This project addresses each of those directly: the SDK removes the "how do I even get telemetry out of my app" friction, the backend gives every event and incident a permanent, tenant-scoped home with an audit trail, the AI service does the first pass of correlation and root-cause reasoning automatically, and the dashboard puts a human approval gate in front of every AI suggestion before anything is considered "decided."

5Backend Explanation (Phase 1)

Confirmed by reading every controller, service, and migration file directly.

Authentication

Handled by AuthController (routes: POST /api/v1/auth/register, POST /api/v1/auth/login). Passwords are hashed with BCrypt; on success the server issues a JWT (signed with JwtService, HS256, minimum 32-byte secret). There is currently no refresh-token, logout, or "get current user" endpoint — the frontend must cache the user object it got at login time.

Organization / Project System

Tenancy is a strict two-level hierarchy: Organization → Project. An organization is created only as a side effect of /auth/register (there's a comment in the code confirming this is intentional for this phase — invite flows for adding more users are explicitly out of scope). OrganizationController only exposes GET /api/v1/organizations/me (read-only). ProjectController supports create/list/get, but no update or delete.

Tenancy checking is explicit, not automatic — every service method takes the caller's organizationId as a parameter and checks it against the resource being accessed, rather than relying on a shared "current tenant" context. A cross-tenant lookup returns 404 (not 403), so it doesn't even reveal that the resource exists.

API Keys

ApiKeyController gives full CRUD: create (the plaintext key is shown once, on creation, then never again — only its hash and a short prefix are stored), list, and revoke (soft-delete via a revokedAt timestamp, not a hard delete). Keys are project-scoped, not organization-scoped — a key can only ever act on the one project it was issued for.

Ingestion APIs

IngestionController exposes POST /api/v1/ingest/logs, /errors, /deployments — all API-key authenticated, all insert-only (no read/update/delete). This is the endpoint the SDK talks to. Logs and errors accept a batch of events in one call; deployments are one-at-a-time.

Incidents

IncidentController supports create, paginated list (filterable by status/severity), get-by-id (with full timeline), and a status-change endpoint. Every incident has a severity (LOW/MEDIUM/HIGH/CRITICAL) and a status that already anticipates the AI agent: OPEN → INVESTIGATING → AWAITING_APPROVAL → RESOLVED/CLOSED. Every mutation appends a row to incident_timeline_entries tagged with one of five entry types, including AGENT_ACTION and APPROVAL — these existed before the AI service was built, specifically so Phase 3 wouldn't need a schema change.

Audit Logs

AuditLogController exposes one read-only, paginated endpoint: GET /api/v1/audit-logs?projectId=. Every mutating action anywhere in the backend calls AuditService.record(...) directly (not via an AOP aspect, not via an event bus) at the end of its own transaction — so the audit row commits or rolls back together with the action it's recording. Audit rows are never updated or deleted.

Database Migrations

MigrationWhat it creates
V1organizations, app_users, projects, api_keys
V2log_events, error_events, deployment_events (the ingestion tables)
V3incidents, incident_timeline_entries

All primary keys are UUIDs generated by Postgres itself (gen_random_uuid()). All schema changes go through Flyway — there is no manual SQL run against the database outside of migrations.

Security Flow

There are two independent Spring Security filter chains, matched purely by URL path, because the two kinds of caller authenticate completely differently:

  1. /api/v1/ingest/** and /api/v1/agent/** → API-key only (the SDK and the AI service both authenticate this way, as a project-scoped key in the X-API-Key header)
  2. Everything else → JWT bearer token only (dashboard users)

An API key can never log into the dashboard, and a dashboard JWT can never call the ingestion or agent endpoints. This is deliberate — it means a leaked SDK key can only ever send telemetry, never read another user's dashboard data.

6SDK Explanation (Phase 2)

Confirmed by reading the SDK source and its 33 passing tests.

Why It Was Created

Any team building a service (a checkout API, a payments worker, etc.) needs a simple way to say "something went wrong, tell the platform" without hand-writing HTTP calls, JSON shaping, batching, and retry logic themselves. The SDK is that missing piece — one Maven dependency, a few config lines, done.

How an External Spring Boot App Uses It

<dependency>
  <groupId>com.irp</groupId>
  <artifactId>incident-spring-boot-starter</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>

Then in application.yml:

incident:
  api-key: irp_live_xxxxx
  endpoint: http://localhost:8080/api/v1/ingest
  service-name: payment-service

That's it — Spring Boot's auto-configuration detects these properties and registers a fully-working IncidentClient bean automatically, plus (in a web app) a servlet filter and an exception resolver, with zero extra code.

What Methods Exist

MethodPurpose
captureException(Throwable[, metadata])Manually report a caught exception
trackEvent(name, metadata)Report any custom named event
markDeployment(version, commitHash)Record that a new version just went out
sendHealthStatus()Report a periodic health heartbeat
flush(Duration), droppedEventCount()Operational helpers (shutdown flush, backpressure visibility)

How It Sends Logs/Errors/Events

Every call above just enqueues an event onto a bounded in-memory queue and returns immediately — it never blocks the caller's request thread. A single dedicated background thread drains the queue, batches events by type, and sends them over java.net.http.HttpClient to Phase 1's /api/v1/ingest/* endpoints with the X-API-Key header. Failed sends retry with exponential backoff on 5xx responses; a 401 (bad key) is logged once and not retried, so a misconfigured key can't hammer the server forever.

Automatic error and latency capture — CONFIRMED IMPLEMENTED Two classes, both auto-registered by IncidentAutoConfiguration only when running inside a real servlet web app:
  • IncidentExceptionCaptureResolver — a Spring HandlerExceptionResolver that catches any uncaught exception thrown by any controller and calls captureException() automatically. No manual try/catch needed anywhere in the host app.
  • IncidentLatencyCaptureFilter — a servlet Filter that times every HTTP request and reports it as an event once it's slower than a configurable threshold.
Verified two ways: (1) the demo app's /demo/boom and /demo/slow endpoints exist specifically to exercise this, and (2) IncidentAutoConfigurationTest (9 tests) and IncidentLatencyCaptureFilterTest (3 tests) all pass.

7AI Service Explanation (Phase 3)

irp-ai-service exists and its core reasoning loop is real and was verified live. The RAG half is not.

Agent Flow

The service exposes exactly one HTTP route: POST /v1/investigations, guarded by a shared internal token. Given an incident_id, it:

  1. Fetches the incident from Phase 1 (using a project-scoped API key, same mechanism as the SDK)
  2. Starts a tool-calling loop against Groq's Llama 3.3 70B model, giving it 5 tools it can call in any order it decides
  3. Once the model calls its final tool, post_investigation_result, the loop stops
  4. The result is validated (Pydantic schema + a guardrail) and posted back to Phase 1 as an AgentSuggestion

The 5 Tools

ToolWhat it doesBacked by real data?
search_errorsRecent error events for a service/time windowReal calls Phase 1
search_logsRecent log lines, optionally filtered by levelReal calls Phase 1
get_recent_deploymentsDeployments around the incident's time windowReal calls Phase 1
search_runbooksSemantic search over uploaded runbooks (RAG)Stub always returns empty
post_investigation_resultThe agent's final structured answerReal

RAG / Vector Database Usage — Designed, Not Implemented

This is the biggest gap in Phase 3. Migration V6 in Phase 1 already created runbooks and runbook_chunks tables, with pgvector installed and an HNSW index ready for semantic search. But:
  • There is no upload endpoint anywhere in Phase 1 to add a runbook
  • There is no embedding pipeline — nothing turns text into vectors
  • app/rag/retriever.py is a literal one-line stub: return []
In short: the database schema for RAG exists, the tool the agent calls exists and is wired up correctly, but there is currently nothing in that database for it to find, ever.

Root Cause Analysis — Real, Verified Live

In an earlier working session, a test incident was created (a NullPointerException in a checkout service, immediately after a version deploy) with realistic matching error/log/deployment rows in the database. The AI service was triggered against it and, using the real Groq model:

  • Correctly called search_errors and get_recent_deployments
  • Correctly correlated the error to the deployment that happened 15 minutes earlier
  • Produced a grounded root cause, a confidence score of 0.86, and two recommended actions (rollback = medium risk, add a null-check = low risk)
  • The suggestion was posted back and the incident automatically moved to AWAITING_APPROVAL

Current Limitations

  • No RAG — see above
  • No automatic trigger — Phase 1 does not call this service when an incident is created; it must be invoked manually (curl or similar)
  • No persisted per-tool-call audit trail — agent_runs/agent_steps tables exist in the database but nothing writes to them; only the final suggestion is saved
  • Open-weight model tool-calling is less reliable than a frontier model — during testing, Llama 3.3 occasionally emitted a malformed tool call (a list instead of an object) that Groq's own schema check rejected; this was caught and fixed with a bounded retry, but it's a known characteristic of the free-tier model choice
  • No automated tests for this module (no pytest files found anywhere in irp-ai-service/)

10Automation Status

Being direct about this, since it's the section most likely to be over-claimed.

What currently exists Partial

  • The AI investigation itself runs without a human writing the analysis — that part is genuinely automated, once triggered
  • A real, backend-enforced human approval gate: an incident with a pending suggestion is forced into AWAITING_APPROVAL, and only a JWT-authenticated dashboard user can move it out of that state — not the AI's own API key
  • Guardrails that cap the AI's confidence score if it can't point to evidence

The "Automations" page UI Only

  • Confirmed by reading dashboard/src/services/automations.ts: it returns hard-coded mock rules, always
  • Confirmed by searching all of project/ for "automation": zero matches — there is no automation/rules table, model, or endpoint anywhere in the backend
  • The page is intentionally labeled "mock data" in its own UI banner

Is automation only UI/mock, or real backend logic?

Both, depending on which "automation" is meant. The AI investigation is real backend logic (Python service + real LLM + real data reads). The "Automations" feature (rules like "auto-notify Slack on critical incidents") is 100% UI mock with no backend at all.

Does human approval exist?

Yes — this is real, not mocked. AgentSuggestionController is JWT-only; the AI service's own API key literally cannot call the approve/reject endpoint. This was a deliberate design decision, not an accident.

What's still needed for real automation

  1. Phase 1 automatically calling Phase 3 when an incident is created (an event listener + HTTP call — designed in the Phase 3 plan, not yet built)
  2. A real domain model + engine for rules ("when X, do Y") backed by a database table and a scheduler/event listener
  3. Real outbound integrations (Slack, PagerDuty, GitHub, generic webhooks) so an approved suggestion can actually do something outside the platform

12What Is Missing / Not Fully Working

No sugar-coating — this is what an honest reviewer would find.

  • Docker-dependent backend tests currently cannot run in this environment — IrpCoreApplicationTests (a context-load test) and EndToEndFlowIT (a full golden-path test) both use Testcontainers to spin up a real Postgres, but Testcontainers reports "Could not find a valid Docker environment" here even though Docker itself is running and was used manually throughout earlier work. This is a local tooling/environment issue, not a defect in the test code itself — the 7 pure unit tests that don't need Docker all pass.
  • Automations page is 100% mock — no backend domain model exists (§10)
  • Integrations page is 100% mock — no OAuth/webhook storage exists anywhere in the backend
  • AI Copilot's cross-incident queue is mock — the backend only has a per-incident suggestions endpoint, not a project-wide one
  • Incident Detail's "Related Signals" tab is mock — no JWT-authenticated (dashboard-facing) endpoint exists for reading logs/errors/deployments; only the API-key-only agent endpoints have this
  • No tests at all for the Python AI service — no pytest files found anywhere in irp-ai-service/
  • No CI/CD pipeline — no .github/workflows or equivalent found anywhere in the repository
  • No agent_runs/agent_steps persistence — the database tables exist (V6 migration) but the AI service never writes to them; only the final suggestion is saved, so there's no fine-grained trace of what the agent searched before it concluded
  • Open-weight model tool-calling reliability — Llama 3.3 on Groq's free tier occasionally produces a malformed tool call; a bounded retry was added, but this is a real characteristic of the current model choice, not fully eliminated
  • No password reset, email verification, or multi-user invite flow — confirmed by reading RegisterRequest.java's own code comment stating this is out of scope for this phase

15Learning Guide — Study Order

The order that will make the least sense to study out of sequence, and why.

  1. Database first — read project/src/main/resources/db/migration/V1 through V6 in order. Every table in the system is defined there; understanding the shape of the data makes every controller afterward make sense immediately.
  2. Auth — AuthController → JwtService → JwtAuthenticationFilter → SecurityConfig. Understand the two-filter-chain split before anything else in security.
